Read this when repeated development iterations need historical awareness.
Persistent notes can prevent duplicate failed proposals and preserve useful
counterevidence. They do not make an untested explanation true or replace a
native Harbor result, evolution ledger, candidate lock, or acceptance gate.

## Keep Three Different Inputs Separate

| Material | Authorized use | Boundary |
| --- | --- | --- |
| Immutable native development jobs and traces | Diagnosis by the authorized development analyst | Keep original bytes and native identities; use the owning skill's permitted projections when it restricts raw access. |
| Development pattern notes and proposal history | Retrieval and mutation by the optimizer | Keep outside candidate bundles, task execution mounts, and publication; exclude independent validation and holdout feedback. |
| Frozen candidate bundle | Procedural guidance available to the task executor | Permit only reviewed, transferable instructions and resources; bind the exact bundle digest in the existing native artifacts. |

These are access roles, not required directory names or a new file format.
Use ignored study-private paths and the owning evolver's existing evidence
records. Never copy native jobs, traces, answer inventories, or optimizer notes
into a candidate merely to make them available during execution.

## Maintain Useful Notes From Authorized Development Evidence

1. Before the first generation, declare whether memory starts empty or comes
   from a prior development campaign. For imports, record the exact snapshot
   digest, source studies, datasets, task-family ancestry, exposure history,
   and any unknown provenance. Have the independent curator check that ancestry
   against the reserved private cohorts without disclosing them. An imported
   summary can carry contamination even when task IDs and answers were removed;
   unproven separation cannot support an unseen-task claim.
2. Build a small index of mechanisms and applicability conditions. Each note
   should distinguish the observed behavior, a causal hypothesis, supported
   remedy, counterevidence, and remaining uncertainty. Link to exact native
   development jobs/trials or permitted projections and their digests. Include
   successes and materially different valid approaches, not only failures.
3. Mark lessons as tentative, supported, disputed, or superseded in ordinary
   prose. Several surfaces from one family are not independent support. Keep
   disagreements and negative transfer visible; do not turn one successful
   rollout or a classification label into a general rule.
4. Link each proposal to its motivating notes, parent/candidate digests, exact
   patch, and already recorded development evaluation and decision. Record
   rejections and abandoned hypotheses too. Derive outcomes from the owning
   native report and ledger; do not ask a model to reconstruct scores or create
   a parallel scoring, ranking, or normalization format.
5. Retain those notes when a candidate is rejected or rolled back. Append a
   correction or a new version when an interpretation changes, preserving the
   prior evidence. Do not overwrite the immutable raw history, silently erase
   a failed proposal, or pretend that a later outcome was known earlier.
6. Freeze and digest-bind the memory snapshot used for each generation in its
   existing mutation/provenance record. Keep the retrieval scope and budget
   explicit: select relevant notes plus linked supporting and conflicting
   evidence instead of injecting the entire archive. Count analysis, retrieval,
   maintenance, and proposal calls in the predeclared development budget.
7. Admit only evidence the owning stage allows for mutation. Independent
   validation and holdout rewards, diagnostics, aggregates, acceptance bits,
   and task content never enter this evolving memory. A library's repeatedly
   consulted "validation" split belongs to development under this repository's
   roles. Do not rename an independent gate to continue after its disclosure.

For a proposed lesson, review its preservation checks and likely failure case
before materializing a child. Local structure checks and a memory citation
establish traceability; only the declared native evaluation can measure the
child's behavior. Whether persistent notes help a particular skill remains an
empirical development question under a matched budget.

## Verify the Task Executor's Actual Access

The executor receives the current task, the declared tools/environment, and
the frozen candidate under the chosen loading policy. Verify this boundary
for development rollouts as well as private evaluation. Development answers
in an accessible wiki can inflate training rewards and allow a candidate to
depend on knowledge that will disappear during independent evaluation.

Before runs, record the effective system prompt and skill-loading policy,
container mounts and build context, file/tool permissions, retrieval sources,
MCP or other services, network routes, shared caches, and session/transcript
reuse. Keep secrets and task contents in private evidence. From the actual
executor identity and runtime, use harmless probes to verify that optimizer
memory, prior raw traces, answer-bearing artifacts, sibling tasks, and private
verifier inputs are inaccessible through those routes. Verify required skill
resources remain available. Reset task sessions and any undeclared cross-task
state. Preserve the probe receipt and its runtime/configuration identity with
the curator's existing access-isolation evidence.

Hashes, ignored files, role names, and an instruction to ignore a directory do
not enforce access. The organizer records curator evidence; it cannot create
container isolation or verify that an external process used the declared
mounts. If the runtime cannot establish the boundary, resolve that limitation
before making an isolated-execution claim. If persistent task memory is itself
the intended treatment, explicitly freeze and compare that system, audit its
contents for leakage, and label the resulting claim accordingly.

## Preserve the Loading Policy in Comparisons

Native skill discovery and loading test whether the agent selects and uses
the skill. Injecting every skill in full into the system prompt removes those
selection failures and changes the context and token burden. Record which
policy, agent configuration, skill set/order, and context budget were used;
keep them matched between baseline and candidate except for the intended
skill treatment. Count the added context in usage. Never combine results from
these policies as if they estimated the same treatment effect.

To claim deployment transfer, evaluate the frozen finalist with the intended
loading policy under the predeclared independent protocol. Changing loading
after seeing an independent result is a new treatment and requires a new study
with fresh private verification.

## Research Basis and Adaptation Limits

[WikiSkill, Sections 3.1–3.2](https://arxiv.org/html/2608.27454v1) motivates
separating immutable traces, accumulated knowledge, and executable skills. It
keeps the wiki through rejected proposals and excludes it from inference. Its
full-injection experiments remove skill triggering as a confounder; they do
not by themselves validate native skill discovery in this repository.

The paper feeds its iterative validation decisions into subsequent proposals.
Under this repository's terminology that adaptive evidence is development.
Preserve the existing one-way independent validation and optional holdout
gates. The practical note workflow and access probes here are local safeguards,
not a reproduced WikiSkill implementation or evidence of a measured gain.
